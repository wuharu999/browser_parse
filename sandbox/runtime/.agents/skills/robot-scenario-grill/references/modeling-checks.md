# 建模检查示例

示例用于识别遗漏，不是预置的客户需求或机器人能力。没有输入支持的步骤标为 candidate，没有数值来源的条件保持 unknown。

## 一、搬箱：状态变化与衔接

输入示例：“让机器人把 A 点的箱子搬到 B 点。”

- 可提取：搬运目标、源点和终点标签。不能推定桌面高度、箱重、抓持方式、路线、机器人型号或定位精度。
- 候选骨架：到达 A 的准备位置 → 观察箱体／相对位姿 → 检查操作条件 → 抓持抬升及复核 → 检查负载通行条件 → 到达 B 并对准 → 放置及复核。
- 不同状态：空载、持物、放置后；运行变量在草稿中没有实测值。建图与空载路线验证不证明持物可通过。
- 关联检查：A／B 到位误差分别与对应操作范围衔接；高度、箱重、重心、姿态和执行器能力约束抓持／抬升；持物外形和遮挡影响导航、避障及负载运输。
- 脱手、定位失效、失稳等是待确认的异常范围。检测能力、恢复条件和人工边界要有节点／缺口，不能默认会重新捡起或自主起身。
- 新回复“箱子实际更重”只更新有关字段及受影响节点，不重编号、不把已有人工判断自行改成不可行。

## 二、洗衣晾衣：等待、循环及环境变化

输入示例：“洗完衣服后把整筐衣服晾起来。”

- 先确认是接手已洗完衣物，还是也要操作洗衣机；不能因提到“洗完”就自动包含洗涤程序。
- 若明确包含洗衣：检查设备和衣物 → 装载及投放 → 启动复核 → Timeout 包裹等待 Action → 洗后观察与继续条件检查 → 取衣及转运。IoT 和物理面板操作可作为候选子树；接口能启动不表示能看见筒内衣物。
- 若存在纸屑污染等超范围情况：明确观察来源、异常与无法判断的处理。客户说“不能处理”不代表机器人已能识别它。
- 晾挂前有 Action 获取剩余对象和挂位初始状态，再进入 Loop。单轮子树包含重新观察、条件检查、取衣／整理／晾挂／复核，以及进度和环境更新。
- Retry 只针对已声明可恢复失败；次数或时间无来源时写未知字段和 issue。对衣物缠绕、反复挂不上，不默认无限试错。
- 已挂衣物会改变空间和可见性；单轮更新影响下一轮。需要整体复核，防止后续动作破坏此前结果。
- “全部完成”要有剩余对象确认方式；数量未知或被跳过的衣物不能自动视作已处理。转人工或部分完成不返回整项成功。

## 三、防鼠板：候选方案不是失败切换

输入示例：“可以开板通过后再关，也可以训练跨越策略。”

- 主树用一个待选 SubTree 表示“通过防鼠板，并保持／恢复规定状态”。
- A、B 各自放入候选组：A 检查可操作性／许可，操作、通过、从另一侧复位及验证；B 检查几何与落脚条件，跨越及站稳复核。
- 未选择前不绑定候选根，更不能生成“开板失败就直接跨越”的 Fallback。
- RL／VLA 放到实现建议，已部署模型、硬件配置、适用范围和实测证据缺失时另建 engineering issue。
- 若客户随后选择 A，保留候选 B 供追溯，只将 A 绑定主树；如果选择导致已确认动作变化，交回确认步骤。

## 四、极少信息与冲突

输入只有“在变电站巡检”：先建立含目标的最小草稿；检查对象、检查结果、是否包含接触操作等是优先问题。不能一上来输出确定的全站路线和热像仪性能。

客户先说“全程无人”，后说“由人开门”：没有明确表示更正时，保留两条来源，标记 conflict，并询问人工边界。客户说“暂时不清楚”保持 unknown，不反复要求同一个客户提供无法获知的机器人测试结论。
